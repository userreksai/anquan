### 1.2 执行规则

- `bash` 代码块在 Linux Bash 中执行；PowerShell 示例单列。不要将终端提示符、Markdown 围栏或说明文字一起复制。
- 每节标注执行位置。新开终端后要重新设置所需变量；两台机器之间的 shell 变量不会共享。
- 构建命令需要对源码、输出和缓存目录有写权限。历史服务器操作使用 root；用 `sudo git clone` 创建的源码通常属于 root，普通构建账号应先取得对应仓库写权限，或在该服务器的 root 维护终端执行，避免混用账号导致权限错误。
- 正式部署、Docker、手工前台运行是可选方式，同一端口、同一生产数据库只运行一个 Master 实例。
- v0.6.8 已安装路径无参数执行会请求一次真实 SSH 登录上报；完整巡检改用 `-scan`，它会扫描并更新可提交的状态。两种操作都会产生实际结果，不是 dry-run。
- 测试章节使用本机回环地址、独立端口和临时目录。涉及删除、停服务或外发消息的命令在对应位置明确标注。

常用变量，在需要的 Linux 终端中设置：

```bash
MASTER_IP='8.217.222.30'
AGENT_IP='49.7.214.217'
MASTER_DB='/data/anquan/anquan.db'
AGENT_BIN='/usr/local/anquan/anquan'
AGENT_OUTPUT='/usr/local/anqu'
# 日志文件按北京时间命名，不要直接用服务器本地日期代替
AGENT_LOG="/var/log/$(TZ=Asia/Shanghai date +%Y%m%d)anquan.log"
```

历史目录手工运行时，只替换 `AGENT_BIN`；输出和状态位置仍由内置配置决定，不能从二进制所在目录推断。

## 2 前置检查和工具

位置：对应 Linux 服务器，任意目录。下面安装命令适用于 Ubuntu / Debian，会安装系统软件。

```bash
uname -m
cat /etc/os-release
hostname
date -Is
timedatectl status
ip -br addr

sudo apt-get update
sudo apt-get install -y git curl ca-certificates sqlite3 jq tcpdump python3
```

Go 与前端工具仅在构建机需要，Agent 目标节点只需要对应架构的二进制：

```bash
command -v go
go version
go env GOOS GOARCH GOPROXY
command -v node
node --version
command -v pnpm
pnpm --version
```

当前 Agent `go.mod` 要求 Go 1.22；Master 声明 Go 1.27.1。Master 自动部署脚本将工具链安装到 `/opt/anquan-tools/go1.27.1`，不会自动加入交互 shell 的 PATH。已通过脚本安装后，可以在当前终端使用：

```bash
export PATH="/opt/anquan-tools/go1.27.1/bin:$PATH"
go version
```

没有这个目录时不能直接照抄 PATH 解决缺失，应先按第 3 节部署脚本安装或在构建机准备满足项目版本要求的 Go。发行版提示的 `apt install golang-go` 版本可能低于项目要求，必须查看 `go version`。

独立 Agent 构建机如果已具备可用的 snapd，可沿用「部署命令」任务中使用的安装方式。该方式修改系统安装状态，安装后仍要核对 Go 版本，不保证不同日期或镜像源返回同一版本：

```bash
sudo snap install go --classic
export PATH="/snap/bin:$PATH"
go version
```

依赖下载超时先检查当前代理和网络；历史任务曾通过下面的临时代理配置完成下载，不修改全局 Go 配置：

```bash
go env GOPROXY GOSUMDB
GOPROXY=https://goproxy.cn,direct go mod download
```

这条命令要在对应仓库根目录执行，代理是否可达以现场网络为准。若需要同一终端后续构建继续使用，执行 `export GOPROXY=https://goproxy.cn,direct`；不要为了下载失败关闭模块校验。

## 3 Master 正式部署和执行方式

### 3.1 原生自动部署

位置：Master 服务器。支持项目脚本指定的 Ubuntu 22.04+ / Debian 12+、systemd、x86_64 或 arm64。需要访问软件源、工具链下载地址和 Go 依赖源。首次部署：

```bash
sudo install -d -m 0755 /opt/anquan
cd /opt/anquan
sudo git clone https://github.com/userreksai/anquan-server-master.git
cd /opt/anquan/anquan-server-master
sudo sh deploy/deploy.sh
```

目录已存在时不要重复 clone，使用第 12 节更新流程。脚本安装依赖和隔离 Go、编译、创建账号与目录、注册并启动 `anquan-master`。已运行的同名服务会被重启。

```bash
sudo systemctl is-enabled anquan-master
sudo systemctl is-active anquan-master
sudo systemctl status anquan-master --no-pager
curl -fsS http://127.0.0.1:10110/healthz
sudo ss -ltnp 'sport = :10110'
sudo ss -lunp 'sport = :55555'
```

预期：服务 `active`，健康接口返回 `{"status":"ok"}`，HTTP 与 UDP 均有监听。自动部署脚本固定检查本机 `10110`；自定义 HTTP 地址后，此检查可能失败，要根据实际地址检查，不能仅凭脚本健康检查失败断言编译失败。

### 3.2 手工构建和 systemd 安装

位置：Master 构建机、Master 仓库根目录；Go 版本满足项目要求。交叉构建不等于在目标 Linux 上执行过测试。

```bash
cd /opt/anquan/anquan-server-master
go mod download
go test ./...
go vet ./...
mkdir -p dist

# 按目标 CPU 二选一构建
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w' -o dist/anquan-master-linux-amd64 ./cmd/anquan-master
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w' -o dist/anquan-master-linux-arm64 ./cmd/anquan-master
```

将目标架构二进制及 `deploy/` 安装文件放到 Master 服务器后，在仓库根目录执行对应的一条：

```bash
sudo sh deploy/install.sh ./dist/anquan-master-linux-amd64
# ARM64 目标改用：
# sudo sh deploy/install.sh ./dist/anquan-master-linux-arm64
```

### 3.3 手工前台运行和只启动后端

位置：Master 开发机、仓库根目录。使用独立目录和端口，Ctrl+C 停止，不设置开机启动：

```bash
mkdir -p dist
CGO_ENABLED=0 go build -trimpath -o dist/anquan-master ./cmd/anquan-master
./dist/anquan-master --help
./dist/anquan-master serve \
  --data-dir ./data-dev \
  --http 127.0.0.1:20110 \
  --udp 127.0.0.1:55556
```

不用页面、但持续接收正式 Agent：安装后只运行 `anquan-master` 服务即可，Web 可以不部署。只允许本机查询 HTTP、仍对外接收 UDP 时，在 Master 服务器编辑环境文件，保留已有其他配置：

```bash
sudoedit /etc/anquan-master.env
```

在该文件设置以下内容，每个键只保留一份：

```text
ANQUAN_HTTP_ADDR=127.0.0.1:10110
ANQUAN_UDP_ADDR=:55555
ANQUAN_TCP_ADDR=:55556
ANQUAN_DATA_DIR=/data/anquan
ANQUAN_SECURE_COOKIE=false
```

```bash
sudo systemctl restart anquan-master
curl -fsS http://127.0.0.1:10110/healthz
```

远程 Web 需要访问后端时，不能把 HTTP 只绑定到回环地址。当前没有“仅启动 UDP、完全关闭 HTTP”的程序参数。

| 启动参数 | 环境变量 | 默认值 |
|---|---|---|
| `--data-dir` | `ANQUAN_DATA_DIR` | `/data/anquan` |
| `--http` | `ANQUAN_HTTP_ADDR` | `:10110` |
| `--udp` | `ANQUAN_UDP_ADDR` | `:55555` |
| `--tcp` | `ANQUAN_TCP_ADDR` | `:55556`，Agent 主动连接以接收配置 |
| `--secure-cookie` | `ANQUAN_SECURE_COOKIE` | `false`，HTTPS 接入后才设置 true |

命令行参数覆盖环境变量；HTTP/UDP 还兼容旧环境变量 `HTTP_ADDR` / `UDP_ADDR`。现有 unit 的 `WorkingDirectory`、`ReadWritePaths` 固定 `/data/anquan`，改变数据目录必须同步修改 unit 或 override 与目录权限。

### 3.4 Docker Compose

位置：Master 宿主机，前后端源码需同级。Compose 方式与原生服务择一，避免端口及数据库冲突。

```bash
cd /opt/anquan/anquan-server-master
docker compose version
docker compose config

# 完整系统：Master + Web
docker compose up -d --build

# 如果只需要后端，改为执行这一条
# docker compose up -d --build master

docker compose ps
docker compose logs --tail=100 master
docker compose logs --tail=100 web
curl -fsS http://127.0.0.1:10110/healthz
```

仅启动 `master` 不会关闭原本已在运行的 `web`；要停已有 Web，单独执行 `docker compose stop web`。数据库绑定 `/data/anquan`。宿主机可直接用 SQLite 查询；容器内未必有 sqlite3 CLI。

日常管理，按需单独执行：

```bash
docker compose logs -f master
docker compose restart master
docker compose stop master
docker compose start master
docker compose stop web
docker compose start web
```

停止 Master 会中断接收；停止 Web 只影响页面。要整体停止并移除容器、网络，可用 `docker compose down`，它不删除此项目绑定的宿主机数据库目录，不需要附加 `-v`。

## 4 Web 正式部署和开发调试

### 4.1 原生 Nginx 部署

位置：Web 服务器，Master 已启动且 `10110/TCP` 可达。首次安装：

```bash
sudo install -d -m 0755 /opt/anquan
cd /opt/anquan
sudo git clone https://github.com/userreksai/anquan-server-web.git
cd /opt/anquan/anquan-server-web

# Web 与 Master 同机时
sudo sh deploy/deploy.sh 127.0.0.1:10110

# 分机时改用这一条，地址以实际 Master 为准
# sudo sh deploy/deploy.sh 8.217.222.30:10110
```

参数为 `IPv4或域名:端口`，不带 `http://` 或路径；当前脚本不接受 IPv6 字面量。脚本会安装独立 Node v24.21.0、pnpm 11.19.0 与 Nginx，编译前端，发布到 `/var/www/anquan/releases/`，更新 `/var/www/anquan/current`，保存上游到源码目录 `.deploy/master-upstream`。

```bash
sudo nginx -t
sudo systemctl status nginx --no-pager
sudo ss -ltnp 'sport = :10111'
curl -I http://127.0.0.1:10111/
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:10111/api/auth/me
```

预期：页面 200；未登录访问 `/api/auth/me` 为 401，说明 API 代理可达。前端没有代理 `/healthz`，访问前端 `/healthz` 可能返回 SPA 页面，不能据此判断 Master 健康。

### 4.2 开发、类型检查、构建与预览

位置：Web 构建机、Web 仓库根目录。准备 Node.js 24 和 pnpm 11.19.0；如果使用原生部署脚本安装的工具链，在当前 shell 设置 PATH：

```bash
case "$(uname -m)" in
  x86_64) ANQU_NODE_ARCH=x64 ;;
  aarch64|arm64) ANQU_NODE_ARCH=arm64 ;;
  *) echo '当前架构不在部署脚本支持范围' ;;
esac
export PATH="/opt/anquan-tools/node-v24.21.0-linux-$ANQU_NODE_ARCH/bin:$PATH"
node --version
pnpm --version
```

自行准备 Node 的构建机可执行 `npm install --global pnpm@11.19.0`。正式服务不需要一直运行 Node；发布后由 Nginx 提供静态文件。

```bash
cd /opt/anquan/anquan-server-web
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm run build

# 开发模式，保持终端运行；上游是第 3.3 节的调试 Master
API_PROXY_TARGET=http://127.0.0.1:20110 pnpm run dev
```

Vite 开发端口为 `10111`，`strictPort` 开启；与同机正式 Nginx 端口冲突时，可显式使用开发端口：

```bash
API_PROXY_TARGET=http://127.0.0.1:20110 pnpm run dev --port 20111
```

构建产物预览，先完成 `pnpm run build`，另择空闲端口：

```bash
API_PROXY_TARGET=http://127.0.0.1:20110 pnpm exec vite preview --host 127.0.0.1 --port 20111
```

预览用于检查构建后的页面，不是正式服务管理方式。项目只声明 `dev`、`typecheck`、`build`、`preview`，没有 `pnpm test` 或 `pnpm lint` 脚本；`build` 本身包含类型检查。

### 4.3 代理与 Nginx 调试

位置：Web 服务器。

```bash
curl -fsS http://8.217.222.30:10110/healthz
sudo nginx -t
sudo nginx -T
sudo tail -n 100 /var/log/nginx/error.log
sudo tail -n 100 /var/log/nginx/access.log
```

## 5 Agent 配置、构建和正式运行

### 5.0 v0.6.3 平台配置启动和安装路径迁移

以下保留 v0.6.3 的历史手工迁移命令，示例 Master 为 `8.217.222.30`。当前新机部署使用第 5.3–5.4 节：无参执行自动安装并启动 agent.service，连接编译时选定的主控 IP（未传构建参数 `-master` 时为 `172.22.0.27`），无需本地 config.age。未下发时不巡检、不采集登录或命令。

```bash
cd /usr/local/anquan
git pull --ff-only
go build -trimpath -o ./dist/anquan.new ./cmd/anqu
sudo systemctl stop agent.service
sudo ./dist/anquan.new -master 8.217.222.30
sudo mkdir -p /etc/systemd/system/agent.service.d
sudo tee /etc/systemd/system/agent.service.d/master.conf >/dev/null <<'EOF'
[Service]
ExecStart=
ExecStart=/usr/local/anquan/anquan -service
Environment=ANQUAN_MASTER=8.217.222.30
EOF
sudo systemctl daemon-reload
sudo systemctl restart agent.service
sudo systemctl status agent.service --no-pager
sudo journalctl -u agent.service -n 50 --no-pager
```

请先更新 Master，使其支持 identity 握手回传，再更新 Agent。旧 identity.conf 中的 ANQUAN_AGENT_IP 已不使用，可删除该手工 IP 环境设置。确认 `/usr/local/anquan/anquan -version` 为 `0.6.3`。Master 须开放 TCP 55556 和 UDP 55555，平台机器列表出现本机后，在配置页面选择本机下发。首次单次运行未取得有效配置时退出 1，但安装和 SSH 入口已完成；常驻服务继续等待。若需要开机常驻，执行 `sudo systemctl enable agent.service`；已有 `agent.timer` 时停止定时器 `sudo systemctl disable --now agent.timer`，使用常驻服务的内部调度。

Agent 自动保存密文 `agent.connection.age` 和加密平台缓存 `config.master.age`，无需手工提供连接文件。旧 `agent.connection.json` 成功加密迁移后删除。主控默认使用编译时选定的 IP（未指定时为 `172.22.0.27`），不依赖 DNS 解析；固定内置 age 密钥用于避免直接读取明文，无法防 root 或逆向提取。v0.6.8 安装后手工无参执行请求一次 SSH 上报：

```bash
sudo /usr/local/anquan/anquan
echo "exit=$?"
```

默认 `login.mode: trigger`，无参或 `-ssh-report` 使用 root 服务的当前有效配置，经本地 Unix IPC 读取并上报匹配的真实认证。同一会话连续执行两次分别产生新事件 ID，不受已消费 `.logins` 游标影响，不扫描文件/进程或修改 Prom。ubuntu 等普通用户无须读取 0600 配置，但必须由服务验证 SSH 上下文；root 未保留 `SSH_CONNECTION` 时可取最近真实认证快照。仅 socket 不可用时 root 可用有效缓存直接上报，不做 TCP 同步；没有真实记录或配置无效时返回 1。

完整单次巡检使用 `sudo /usr/local/anquan/anquan -scan`，该流程才启动时限时同步配置并扫描。需要 v0.6.7 每秒增量去重行为时，明确配置 `login.mode: poll`；poll 拒绝执行上报请求。两种登录方式都要求 `login.enabled: true`、可读数据源和非空 UDP `server`；生产推荐 journal。UDP 接收端离线时不保证入库或机器人送达，本地发送日志不能替代主控查询。

### 5.1 配置文件准备与常见修正

位置：Agent 构建机、Agent 仓库根目录。历史现场为 `/usr/local/anquan`。首次获取仓库可执行 `git clone https://github.com/userreksai/anquan.git`，后续进入实际检出目录。

```bash
cd /usr/local/anquan
go version
test -e config.yaml || cp configs/config.example.yaml config.yaml
chmod 0600 config.yaml
vi config.yaml
```

以下是需要核对的配置片段，不是整个配置文件，也不要追加到已有同名键后面：

```yaml
server:
  - 8.217.222.30:55555
login:
  enabled: true
  mode: trigger
  source: journal
  journal_command: journalctl
  initial_lookback_hours: 24
  timeout_seconds: 10
  max_records: 1000
setup:
  logs: /var/log/时间anquan.log
  prom: /var/lib/node_exporter/textfile_collector/process_monitor.prom
  interval_seconds: 300
```

server 是 UDP 接收列表，支持 [192.168.0.1,192.168.0.2] 和显式 IP:端口；ANQUAN_MASTER 独立指定 TCP 配置主控。Agent v0.6.6 自动取得到主控路由所选的本机网卡 IP，无需 agent_ip；Nginx 中转地址由主控单独记录为连接来源。平台下发后自动生效，server: [] 仅关闭 UDP。

历史任务中出现重复 `server` 错误时：

```bash
grep -nE '^server:' config.yaml
nl -ba config.yaml | sed -n '48,70p'
vi +55 config.yaml
```

只保留一个顶层 `server`；多个主控放在同一个列表中。行号只是历史示例，以当前错误位置为准。

### 5.2 构建命令与全部构建参数

位置：Agent 构建机、Agent 仓库根目录。

```bash
go mod download
go test ./...
go vet ./...

# Linux x86_64
go run ./cmd/anqu-build -config ./config.yaml -output ./dist/anqu-linux-amd64 -goos linux -goarch amd64

# Linux ARM64
go run ./cmd/anqu-build -config ./config.yaml -output ./dist/anqu-linux-arm64 -goos linux -goarch arm64

# 沿用历史产物名，仅适用于目标与构建机架构一致
go run ./cmd/anqu-build -config ./config.yaml -output ./dist/anquan -goos linux -goarch "$(go env GOARCH)"

# 自定义主控 IP；不需要本地 YAML 也可构建
go run ./cmd/anqu-build -output ./dist/anquan -goos linux -goarch amd64 -master 192.168.1.100

# 查看构建器帮助
go run ./cmd/anqu-build -help
```

| 参数 | 用途 |
|---|---|
| `-config` | 可选构建机 YAML 路径，未指定时只生成 Agent |
| `-master` | 内置默认主控 IP，单个 IPv4 或 IPv6 地址，不带端口；省略或空值默认 `172.22.0.27`，新机自动安装服务也使用此地址 |
| `-output` | 输出程序路径，未指定时为 `anqu`，Windows 为 `anqu.exe` |
| `-goos` | 目标系统，默认 Linux |
| `-goarch` | 目标 CPU，默认构建器当前架构 |
| `-go` | 供构建器调用的 Go 编译器路径，默认 `go` |

已安装服务中显式设置的运行参数 `-master` 优先于新二进制的编译默认地址；单纯远程升级 Agent 不会自动切换已有服务的主控，迁移主控还需更新服务启动参数并重启。

使用隔离工具链而没有设置 PATH 时，外层命令和 `-go` 都指定：

```bash
/opt/anquan-tools/go1.27.1/bin/go run ./cmd/anqu-build \
  -go /opt/anquan-tools/go1.27.1/bin/go \
  -config ./config.yaml -output ./dist/anqu-linux-amd64 -goos linux -goarch amd64
```

普通 `go build ./cmd/anqu` 使用同一固定内置 age 密钥，可用于生产 Agent。构建器的 `-config` 为可选参数，仅同时生成初始 `config.age`，不将 YAML 嵌入程序；节点没有 `-config`、`-check-config` 或导出配置参数。

### 5.3 传输和单次验收

位置：构建机。下例传到历史 Agent 的 `/tmp`；目标用户、地址和架构须对应实际机器。

```bash
scp ./dist/anqu-linux-amd64 root@49.7.214.217:/tmp/anqu-linux-amd64
```

位置：Agent 服务器。下面为首次安装，需 root 和 systemd。无参数执行上传文件时，自动安装标准目录、SSH 入口和 agent.service，state/logs/textfile 由实际功能按需创建，执行 daemon-reload 与 enable --now，服务连接编译时选定的主控 IP 和 55556/TCP，安装进程退出 0；未传构建参数 `-master` 时主控为 `172.22.0.27`，无需在节点人工设置。主控暂时不可达时后台服务持续重连；运行参数改用自定义域名时，DNS 暂时不可用也会持续重连。可选配置、缓存和连接文件只在目标不存在时从原程序旁复制，不覆盖已有目标配置，不删除上传目录源副本；旧连接 JSON 的加密迁移只处理固定运行目录。已有常驻服务更新请走第 12 节，先停止旧实例再替换二进制，并核对旧 drop-in 是否覆盖 ExecStart。

```bash

chmod 0700 /tmp/anqu-linux-amd64
/tmp/anqu-linux-amd64 -version
/tmp/anqu-linux-amd64 -help
sudo /tmp/anqu-linux-amd64
ANQU_EXIT=$?
printf 'Agent exit code: %s\n' "$ANQU_EXIT"
```

v0.6.5 也支持在 `/usr/local` 下以 `anquan` 为文件名上传并直接执行。安装器会先将自身保留到同目录唯一 `anquan.upload-*` 备份，再创建 `/usr/local/anquan/`，继续安装和启动服务。v0.6.9 无参自动安装和服务启动成功后删除本次备份，失败时保留并提示重试路径；历史备份不自动扫描删除。v0.6.4 遇到这种同名路径会报 `not a directory`；旧程序可先改名为未占用的 `anquan-upload` 再执行。不要删除上传程序或已有配置目录。

`-help` 和 `-version` 不执行安装。部署后以 `/usr/local/anquan/anquan -version` 确认版本；旧服务的 ExecStart 也须改到固定路径。

普通启动同时写入 `/usr/local/ssh-init.sh`，建立 `/etc/ssh/sshrc -> /usr/local/ssh-init.sh`；已有不同脚本或 sshrc 先备份 `.anquan.bak` 再替换。两行脚本无须修改，sshrc 按登录用户权限向 root 服务请求上报，由服务读取 journal 和配置；普通用户不需要读取 0600 文件。服务校验非 root 的调用者和 SSH 上下文，Unix socket 位于 `/run/anquan/.ssh-execution/agent.sock`。用户级 `~/.ssh/rc` 可能优先于系统 sshrc。Agent 不修改 sshd_config。脚本固定内容及检查命令：

```bash
# /usr/local/ssh-init.sh 内容
#!/bin/sh
/usr/local/anquan/anquan </dev/null >/dev/null 2>&1
```

```bash
sudo readlink /etc/ssh/sshrc
sudo cat /usr/local/ssh-init.sh
sudo ls -l /usr/local/anquan/anquan /usr/local/anquan/agent.connection.age
```

### 5.4 正式常驻服务

位置：Agent 服务器。新机首次无参执行已自动创建并启动 agent.service，实际 ExecStart 为 `/usr/local/anquan/anquan -service -master 172.22.0.27`。下面只检查安装结果：

```bash
sudo systemctl is-enabled agent.service
sudo systemctl status agent.service --no-pager
sudo systemctl cat agent.service
sudo journalctl -u agent.service -n 100 --no-pager
```

预期：取得有效配置后立即扫描，默认每 300 秒继续；独立 UDP 心跳每 30 秒发送，无有效配置时保持 TCP 连接等待下发。关闭 SSH 终端不影响 systemd 服务。手工前台调试可运行 `sudo /usr/local/anquan/anquan -service`，但必须先停止同配置的常驻实例，Ctrl+C 会结束前台程序。

### 5.5 可选 oneshot 加 timer

位置：Agent 服务器，已传输仓库 `deploy/anqu-oneshot.service` 和 `deploy/anqu.timer` 到当前目录。这组会停止常驻模式，按需选择，不与上一方案同时启用。

```bash
sudo systemctl disable --now anqu.service
sudo systemctl disable --now agent.service
sudo install -m 0644 ./anqu-oneshot.service /etc/systemd/system/anqu-oneshot.service
sudo install -m 0644 ./anqu.timer /etc/systemd/system/anqu.timer
sudo systemctl daemon-reload
sudo systemctl enable --now anqu.timer
sudo systemctl list-timers --all anqu.timer
sudo journalctl -u anqu-oneshot.service -n 100 --no-pager
```

timer 在启动后 1 分钟执行，随后每次任务结束后等待 5 分钟；它不读取 `setup.interval_seconds` 来安排系统 timer。单次运行结束后没有持续心跳，Master 可能在两轮之间显示异常离线。要求持续在线状态时使用 `-service`。

## 7 不用页面查询数据

位置：Master 服务器。安装 `sqlite3` 后，不需要前端，也不需要另开数据库服务。以下均以只读方式访问正式数据库；sudo 用于读取默认 `0600` 权限文件。

| 运行情况 | 查询已保存数据 | 接收新的 Agent 数据 |
|---|---|---|
| Master 运行、Web 停止 | SQLite 或 API 均可 | 可以 |
| Master 与 Web 都停止 | SQLite 可以，API 不可 | 不可以 |
| 使用独立 UDP 文件接收器 | 查询它保存的文件 | 接收器必须保持运行，不自动写入 Master 数据库 |

### 7.1 确认库、表和数据量

```bash
MASTER_DB='/data/anquan/anquan.db'
sudo test -f "$MASTER_DB"
sudo sqlite3 -readonly "$MASTER_DB" '.tables'
sudo sqlite3 -readonly "$MASTER_DB" 'PRAGMA user_version;'
sudo sqlite3 -readonly "$MASTER_DB" '.schema events'
sudo sqlite3 -readonly -header -column "$MASTER_DB" "
SELECT 'machines' AS table_name,COUNT(*) AS count FROM machines
UNION ALL SELECT 'events',COUNT(*) FROM events
UNION ALL SELECT 'webhooks',COUNT(*) FROM webhooks
UNION ALL SELECT 'outbox',COUNT(*) FROM outbox;"
```

当前数据库版本应为 2。文件只有 4 KiB 但 WAL 较大不一定异常；查询原始路径会读取已提交的 WAL，不要删除 `.db-wal` 或 `.db-shm`。

### 7.2 机器和最近接收时间

```bash
sudo sqlite3 -readonly -header -column "$MASTER_DB" "
SELECT ip,host,alias,source_ip,reported_ip,
 datetime(last_seen/1000,'unixepoch') AS last_seen_utc,
 datetime(last_seen/1000,'unixepoch','+8 hours') AS last_seen_beijing,
 interval_seconds,heartbeat_interval_seconds,
 CASE WHEN heartbeat_interval_seconds>0
   THEN max(heartbeat_interval_seconds*3,30)
   ELSE max(interval_seconds*3,120) END AS offline_after_seconds
FROM machines ORDER BY last_seen DESC;"
```

`source_ip` 是 Master 观察到的 UDP 来源，`reported_ip` 是报文上报身份；SSH 登录来源在事件 `data.source_ip` 中。心跳只更新机器，不写 `events`；只有心跳时，机器有数据、事件数为 0 可以是正常状态。

### 7.3 最近完整事件和分类数量

```bash
sudo sqlite3 -readonly -header -column "$MASTER_DB" \
  'SELECT type,COUNT(*) AS count FROM events GROUP BY type;'

sudo sqlite3 -readonly -line "$MASTER_DB" "
SELECT id,event_id,machine_ip,host,type,
 datetime(time/1000,'unixepoch','+8 hours') AS event_time_beijing,
 datetime(received_at/1000,'unixepoch','+8 hours') AS received_time_beijing,
 status,notes,data
FROM events ORDER BY time DESC,id DESC LIMIT 20;"
```

上面明确显示北京时间。若要显示本地系统时区，SQLite 可用 `'localtime'`；要显示 UTC，去掉 `'+8 hours'`。原始值是毫秒，使用 `datetime()` 前必须除以 1000。

### 7.4 告警明细与文件 MD5


## 8 接收与 SSH 登录调试完整链路

### 8.1 第一步：核对 Master 进程、路径和监听

位置：Master 服务器。

```bash
sudo systemctl status anquan-master --no-pager
sudo journalctl -u anquan-master -n 100 --no-pager
sudo ss -lunp 'sport = :55555'
curl -fsS http://127.0.0.1:10110/healthz
```

核对启动日志中的 `database` 是否就是查询文件。Docker 则使用 `docker compose ps`、`docker compose logs --tail=100 master` 和 `docker compose port master 55555 --protocol udp`。只有监听和健康检查正常，尚不能证明任何事件已经到达。

### 8.2 第二步：抓包同时触发扫描

位置：Master 服务器，先开抓包，另一个终端到 Agent 触发或等待扫描。

```bash
# 只看报文到达，最多 70 秒或 10 个数据报
sudo timeout 70 tcpdump -ni any -nn 'udp dst port 55555' -c 10

# 要检查事件类型时使用这条，避免 -c 太小只抓到心跳
sudo timeout 70 tcpdump -ni any -nn -s 0 -A 'udp dst port 55555'

# 需要留档时，保存 pcap，再离线查看
sudo timeout 70 tcpdump -ni any -nn -s 0 -w /tmp/anqu-udp.pcap 'udp dst port 55555'
sudo tcpdump -nn -A -r /tmp/anqu-udp.pcap
```

`timeout` 到期通常返回 124，不等于 Agent 故障。70 秒足以覆盖正常的 30 秒心跳，但不能保证覆盖下一次默认 300 秒巡检；要等巡检，延长抓包时间或在允许的维护窗口执行一次扫描。pcap 包含监控数据，应按日志资料保管。

位置：Agent 服务器，检查发送进程、路线和日志。

```bash
MASTER_IP='8.217.222.30'
pgrep -af anqu
ip -br addr
ip route get "$MASTER_IP"
sudo systemctl status anqu.service --no-pager
AGENT_LOG="/var/log/$(TZ=Asia/Shanghai date +%Y%m%d)anquan.log"
sudo grep '"event":"scan_complete"' "$AGENT_LOG" | tail -n 3
```

完整巡检调试使用 `-scan`，仅在没有同配置常驻实例时手工运行；已有服务时优先等下一轮。要立即重跑完整巡检，可在维护窗口重启实际服务。v0.6.8 SSH 触发上报另用无参或 `-ssh-report`，可在 root 服务运行期间调用，无须重启完整巡检。

```bash
# 仅在没有同配置常驻实例时
sudo /usr/local/anquan/anquan -scan
```

确认 `notifications.server` 是 Master，`notifications.ip` 是 Agent 身份。抓包仅证明报文到了抓包位置；继续查数据库和主控日志才算验证成功。

### 8.3 第三步：确认 UDP 内容和入库

位置：Master 服务器。

```bash
sudo journalctl -u anquan-master --since '10 minutes ago' --no-pager
sudo sqlite3 -readonly -header -column /data/anquan/anquan.db \
  'SELECT ip,host,last_seen FROM machines; SELECT type,COUNT(*) FROM events GROUP BY type;'
```

重点查 `UDP event rejected`、数据库错误及实际报文 `type`。主控对拒绝日志做节流，未看到逐条拒绝日志不代表每条报文都被接受。UDP `nc -z -u` 或 `sendto()` 返回成功也不能替代入库验证。

### 8.4 SSH 登录为空时，完整复现

位置：操作员电脑终端。保持原连接，另开到 Agent 的新 SSH 认证，避免连接复用：

```bash
ssh -o ControlMaster=no -o ControlPath=none root@49.7.214.217
```

位置：新登录的 Agent 终端。查看系统是否实际记录新认证；`journalctl --since` 使用节点系统本地时区。

```bash
hostname
date -Is
sudo journalctl --since '5 minutes ago' --no-pager -o short-iso \
  | grep -E 'sshd.*Accepted '

# 需要扩大范围时
sudo journalctl -n 3000 --no-pager -o short-iso \
  | grep -E 'Accepted (password|publickey|keyboard-interactive)' | tail -n 10
```

默认 trigger 模式在当前 SSH 会话手工请求一次上报，再查看执行日志；无需等 300 秒巡检。普通用户请求需要 root agent.service 正常运行，并已应用有效 trigger 配置、可读 journal 和非空 server：

```bash
AGENT_LOG="/var/log/$(TZ=Asia/Shanghai date +%Y%m%d)anquan.log"
/usr/local/anquan/anquan -ssh-report
echo "exit=$?"
sudo grep '"event":"ssh_execution_complete"' "$AGENT_LOG" | tail -n 2
# 显式 mode: poll 时改看下面两类日志；此模式不接受 -ssh-report。
sudo grep '"event":"login_result"' "$AGENT_LOG" | tail -n 1
sudo grep -E '"event":"(ssh_poll_complete|ssh_login_error)"' "$AGENT_LOG" | tail -n 2
sudo grep '"event":"ssh_login"' "$AGENT_LOG" | tail -n 5
```

位置：Master 服务器，查第 7.5 节的 SSH SQL。判断依据：

| 现象 | 含义与下一步 |
|---|---|
| 没有新 `Accepted` 行 | 未产生新认证，开新 shell 或复用连接不一定算新登录 |
| trigger 有新认证但执行失败 | 核对服务已应用配置、mode、server、journal 读取权限、SSH_CONNECTION 及调用者上下文；查看命令错误与执行日志 |
| poll 的 `records: []` | 检查采集时间、数据源、读取权限、游标和分页积压 |
| poll 的 `record` 有旧记录、`records` 为空 | 最近已知登录存在，本页新增为 0，不会重发旧登录 |
| 报文只有 `heartbeat`、`scan_summary`、`alert` | 不能用它们证明 `ssh_login` 已发送 |
| `scan_summary.data.logins=0` | trigger 服务巡检不补发登录，poll 也可能已由独立 worker 读走；须查执行/poll 日志，不能只看摘要 |
| 抓到真实 `ssh_login`，数据库无记录 | 核对接收进程、数据库路径、拒绝/入库错误和事件去重 |
| `datagrams_sent=N` 且无错误 | 仅说明本地发送，仍需 Master 查询确认 |

历史任务曾验证旧增量模式中新认证的采集；v0.6.8 应区分 mode：trigger 连续执行两次应有两个不同执行 ID，相同 `source_record_id` 和真实 `login_time`，Master 分别入库通知；poll 沿用游标去重，重启不自动补传旧登录。不要删除 `.logins` 来验证 trigger，它不消费该状态。生产需继续确认实际数据库和机器人收到通知，本地 UDP 成功不构成端到端验收。

### 8.5 防火墙与进程规则

位置：对应服务器，仅查看，不修改现有网络策略。

```bash
sudo ufw status verbose
sudo nft list ruleset
```

工具未安装时按实际防火墙管理方式检查。云安全组不一定能从以上输出看到。需要允许的路径是 Agent → Master `55555/UDP`、Web → Master `10110/TCP`、浏览器 → Web `10111/TCP`；Agent 本身不需要开放 UDP 55555 入站。

Agent 报“sshd 缺失”时，在 Agent 查看真实命令行：

```bash
pgrep -a sshd
for ANQU_PID in $(pgrep -x sshd); do
  printf 'PID %s: ' "$ANQU_PID"
  sudo cat "/proc/$ANQU_PID/cmdline" | tr '\0' ' '
  printf '\n'
done
```

进程规则是空白归一化后的完整命令精确匹配。实际命令被改写为 `sshd: ... [listener] ...` 时，与 `/usr/sbin/sshd -D` 不相等；不能仅凭规则不匹配判断 SSH 服务停止。

## 11 不启动 Master，临时接收到 JSONL 文件

该方式是独立调试接收器，不包含 Master 校验、SQLite 入库、去重或 Webhook，也不是原有主控的离线缓存。进程停止后就无法接收，收到的文件不会自动导入 Master。

位置：调试接收机任意可写目录，需要 Python 3。默认监听 `55556/UDP`，避免占用 Master 的 `55555`。要让真实 Agent 发到这里，须修改测试 Agent 的内置 `server` 端口并重新构建；不要据此改动正式 Agent。用同一 IP 的 55555 时，必须先确保该端口没有 Master 占用。

```bash
umask 077
python3 -u - 0.0.0.0 55556 ./anqu-udp-capture.jsonl <<'PY'
import base64, datetime, json, os, socket, sys
bind_ip, port, output = sys.argv[1], int(sys.argv[2]), sys.argv[3]
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
    sock.bind((bind_ip, port))
    print(f"监听 {bind_ip}:{port}，追加保存到 {output}；Ctrl+C 结束", flush=True)
    with open(output, "a", encoding="utf-8") as log:
        try:
            while True:
                payload, remote = sock.recvfrom(65535)
                record = {"received_at": datetime.datetime.now(datetime.timezone.utc).isoformat(),
                          "source_ip": remote[0], "source_port": remote[1],
                          "bytes": len(payload)}
                try:
                    record["packet"] = json.loads(payload.decode("utf-8"))
                except (UnicodeDecodeError, json.JSONDecodeError):
                    record["raw_base64"] = base64.b64encode(payload).decode("ascii")
                line = json.dumps(record, ensure_ascii=False)
                log.write(line + "\n")
                log.flush()
                os.fsync(log.fileno())
                print(line, flush=True)
        except KeyboardInterrupt:
            pass
PY
```

另一个终端查询接收文件：

```bash
tail -n 20 ./anqu-udp-capture.jsonl
jq -c 'select(.packet? | objects | .type=="ssh_login")' ./anqu-udp-capture.jsonl
jq -c 'select(.packet? | objects | .type=="alert")' ./anqu-udp-capture.jsonl
```

没有 Master 时，也可以用 tcpdump 抓取到达网卡的 UDP，但抓包不是业务接收或入库，不能保证与程序接收结果相同。

### 12.1 Master 数据备份

位置：Master 服务器。下面使用 SQLite `.backup` 获取一致性快照，不是单独复制运行中的 `.db`；大库备份会增加 I/O。备份包含账号哈希、会话、Webhook 地址和通知任务，应按敏感数据保管。

```bash
ANQU_BACKUP="/var/backups/anquan/$(date +%Y%m%d_%H%M%S)"

sudo sqlite3 -readonly /data/anquan/anquan.db ".backup '$ANQU_BACKUP/anquan.db'"
sudo chmod 0600 "$ANQU_BACKUP/anquan.db"
sudo sqlite3 -readonly "$ANQU_BACKUP/anquan.db" 'PRAGMA quick_check;'
```

若选择停机备份整个目录，停止后才打包，期间不能接收上报；systemd 与 Docker 选择实际部署方式：

```bash

sudo tar -C /data -czf "$ANQU_BACKUP/anquan-data.tar.gz" anquan
sudo chmod 0600 "$ANQU_BACKUP/anquan-data.tar.gz"
sudo systemctl start anquan-master
```

Docker 将两条 systemctl 命令换为 `docker compose stop master` 和 `docker compose start master`。如果打包失败也应检查并恢复所需服务，不能把一直停机当作备份完成。

### 12.3 Agent 二进制更新

位置：Agent 服务器，新二进制已传到 `/tmp/anqu-linux-amd64`，架构对应本机。这组短暂停服务并备份当前程序和状态；不清空基线。

```bash
sudo systemctl start anqu.service
sudo systemctl status anqu.service --no-pager
sudo journalctl -u anqu.service -n 50 --no-pager
```

状态路径要按实际配置调整；timer 部署先停止 timer 与正在执行的 oneshot。上述备份或安装失败时，先确认旧二进制是否仍在，再恢复服务，不要忽略失败后继续覆盖。

在同一 shell 中需要回退程序，可恢复刚才备份的程序；已推进的新状态是否与旧程序、旧配置兼容要先核对：

```bash

sudo mv -f /usr/local/anquan/anquan.next /usr/local/anquan/anquan && \
sudo systemctl start anqu.service
```

修改文件规则或进程白名单导致基线范围不兼容时，系统会报错而不是自动重置。确需初始化新基线，应在停服务、备份后只迁移对应状态；这会改变检测对比起点，不要顺带移动 `.logins`。

```bash

sudo systemctl stop anqu.service
ANQU_STATE_BACKUP="/var/backups/anqu-agent/state-$(date +%Y%m%d_%H%M%S)"

sudo systemctl start anqu.service
```

进程清单状态为 `.processes`，仅需要重建进程基线时替换该后缀。构建机私有 YAML 也应单独备份，节点二进制无法作为可维护的配置源文件。

## 13 常见错误和正式验收顺序

| 现象 | 判断与处理 |
|---|---|
| `go: command not found` | 构建机缺少 Go 或隔离工具链没加入 PATH，先查第 2 节 |
| Go 依赖下载超时 | 查看 `go env GOPROXY`、网络和代理，不需要反复重装程序 |
| `mapping key server already defined` | 编辑 YAML，只保留一个顶层键；多个目标用列表 |
| `embedded configuration unavailable` | 使用了普通 go build 的产物，重新用 `anqu-build` 构建 |
| 改 YAML 仍发旧 IP | 没有重新构建、没有替换实际运行文件，或服务指向另一产物 |
| `address already in use` | 同端口存在旧进程，检查 ss、systemd 与 Docker，勿并行启动 |
| 数据库空、无抓包 | 核对 Agent 是否运行、server、UDP 目标、安全组与防火墙 |
| 抓包有数据、数据库空 | 看具体 type、主控拒绝日志、实际数据目录和入库错误 |
| SSH 查询空但有进程告警 | 两类事件不同，按第 8.4 节验证新认证与本轮 records |
| Master 停机后历史缺口 | UDP 无自动补传，回查 Agent 本地文件；不要假设重启会补齐 |
| timer 模式反复离线 | 每轮退出后无持续心跳；需要持续在线时切换常驻服务 |
| Web 502 | 检查上游地址、10110/TCP 和 Nginx 错误日志 |
| API 401 / 改密后掉线 | 会话缺失、过期或被撤销，重新登录 |
| Webhook HTTP 成功但仍失败 | 飞书/企业微信还需要有效 JSON 业务确认码为 0 |
| `.db` 很小、WAL 较大 | WAL 模式正常可能如此，不能删 WAL 或仅按主库大小判断数据量 |
| `baseline ... changed` | 配置范围与旧基线不兼容，先备份，再按模块显式迁移 |

正式验收按以下顺序完成，每一步都保留对应结果：

1. Master 健康接口正常，UDP 55555 监听，数据库路径正确。
2. Agent 标准二进制版本正确，内置目标与身份正确，单次扫描输出可读。
3. Agent 常驻服务启动，Master 机器表出现对应 IP；观察 30 秒心跳刷新接收时间。
4. 查看巡检摘要和真实告警；确认 `collection_success` 与告警数量的含义不同。
5. 新建一次独立 SSH 认证，确认系统日志、Agent records、UDP 类型和 Master 事件能对应。
6. Web 登录、查询和筛选正常；未登录 API 为 401。
7. 对专用通知地址做测试，再用新告警验证自动通知；通过测试库验证重试与重启续投。
8. 确认开机启动、备份可读、日志和历史指标的保留策略；记录实际端口与数据目录。
