# 安全检测 Agent：需求与实现说明（v0.4.0）

本文记录 anquan Agent 的检测行为；主控和前端分别由 anquan-server-master、anquan-server-web 提供。Agent 使用兼容 v1 的 UDP 数据报接口上报。完整配置和部署命令见 [README](../README.md) 与 [配置模板](../configs/config.example.yaml)，主控对接字段见 [协议文档](agent-master-protocol.md)。

## 需求与实现

| 需求 | 实现与验收依据 |
|---|---|
| 服务启动记录当前时间 | `-service` 启动写入 `service_started`，单次启动写入 `agent_started`；包含北京时间、主机名、PID 和版本 |
| 每次执行记录当前机器检测结果 | `scan_started`、完整模块结果、逐条告警和登录事件、`scan_complete` 同时写标准输出和当天 JSONL 日志；正常结果也保留 |
| 无 MD5 初始化，之后按变更后的结果比较 | `FilesMonitoring.fils/dir/search` 未提供 MD5 时建立持久化基线；之后比较上次成功扫描并在报告、日志成功后提交下一基线 |
| 多路径、多允许 MD5 | 同条规则 `路径1|路径2,MD5a,MD5b,MD5c`；每个文件各自命中任一允许值才正常，允许值不用全部使用 |
| 只有一个文件匹配时通知 | 不匹配文件产生 `md5_mismatch`；规则明细记录匹配、不匹配和缺失数量，每个文件保留实际 MD5 与允许集合 |
| 缺失文件通知 | 每轮产生 `missing`；首次缺失不妨碍其他正常文件建立基线，后来出现时产生 `added` |
| 目录文件增加、删除、内容变化 | 递归处理普通文件，记录 `added/deleted/modified`、路径和前后 MD5；固定 MD5 规则仍检查目录成员增删 |
| 按文件名从多个根目录搜索 | `文件名,目录1|目录2[,MD5...]` 递归精确匹配文件名，检查每个匹配文件；无结果产生 `not_found` |
| 进程适配多个系统 | `ProcessMonitoring.exists` 每行 `命令1|命令2|...`，任意一个完整命令行匹配即正常 |
| 进程列表及白名单 | `Process: {}` 开启首次列表初始化和滚动比较；以完整命令和实例数量检测增删；白名单只抑制列表变化告警，不免除 exists 检查 |
| 每次 SSH 登录有记录 | 默认增量读取 journal 的 sshd/sshd-session 成功认证记录，持久化游标，记录用户、来源 IP、登录时间、认证方式及可获得的终端 |
| 北京时间零点切日志 | `setup.logs` 中的 时间/{date} 生成 `YYYYMMDD` 文件；每次写入按 UTC+08:00 日期选择日志，与宿主机时区无关 |
| 每轮一个时间命名的 .prom | `setup.prom` 生成含纳秒采集时间的文件，不覆盖历史；默认间隔 300 秒 |
| UDP 对接主控 | 配置 `server: [IP:port]` 后发送 scan_summary 心跳、alert、ssh_login 数据报；机器 IP 支持自动获取或 agent_ip 固定；空列表保持本地记录 |

## 配置与构建方式

沿用现有“构建机 YAML → 校验并加密内置 → 节点只部署程序”的流程。修改配置后重新运行 `anqu-build`；目标节点不读取外部 YAML。新格式保留用户约定的 `fils` 拼写及大小写，未知字段和非法哈希会在构建阶段报错。`md51` 等仅是需求描述里的占位值，实际配置必须填写 32 位十六进制 MD5。

文件监控中 `|` 表示每个路径都要检查；进程 exists 中 `|` 表示任意一个备选满足即可。两者语义不同。不存在文件、MD5 不匹配和必须进程缺失都属于检测告警，区别于采集权限不足或状态文件损坏等执行错误。

首次已知不存在的根路径会告警，同时对其余成功读取的文件建基线。权限不足、文件读取中变化、目录遍历错误等不完整扫描则保留旧基线，不能当成删除。固定 MD5 允许值始终由配置决定，不会被当前内容覆盖。符号链接不跟随；已跟踪对象被替换为链接或特殊文件时显式报错。

旧 md5、existence 配置保持兼容。新文件、进程和登录状态分别保存在 `state_file.files`、`state_file.processes`、`state_file.logins`，不自动把旧基线套用到新规则。监控范围或允许集合变更需要停止服务、备份相应状态并明确重建；详见 README。

## 日志与输出

日志是每行一个 JSON 对象：统一外层字段为 time、host、event、data。模块结果保留每个受检文件的实际哈希和状态、规则统计、完整进程清单，以及本轮全部新增登录。告警同时单独输出为 `alert` 事件，成功登录输出为 `ssh_login` 事件。基线更新前先发布报告及详细日志；崩溃可能重复记录，但不会故意消费尚未写出的变更。

每轮还生成完整 JSON 报告、历史 .prom 和固定的 `output_dir/textfile/anqu.prom`。历史指标使用 `anqu_snapshot_` 前缀并附加 host/run_id 标签，避免多个文件中同名同标签样本冲突；最新指标使用稳定的 `anqu_` 前缀。历史文件会持续增长，由部署方制定保留期限。扫描开始时间写入文件名，指标包含采集完成时间。

单次执行退出码：0 为完成且无告警，2 为完成且发现告警，1 为配置、采集、输出、状态保存或 UDP 发送错误。常驻服务启动后立即巡检，之后按 interval_seconds 节拍运行；不并发扫描，慢于周期时跳过过期节拍。单轮错误保留在日志和报告中，并继续下一轮；收到停止信号后完成当前扫描再退出。

## SSH 登录覆盖范围

- journal 是默认生产方式：首次默认回看 24 小时；之后按持久化游标续读。max_records 限制每轮处理的事件数，积压留给后续轮次，不只取最新一条。
- authlog 支持 auth.log/secure 成功认证行、字节偏移和保留的未压缩轮转文件。初次只读当前文件；轮转历史缺失、已压缩或截断到无法恢复时显式报错。
- jsonl 用于自定义日志和演示，支持同一时间多个事件、分页及重启去重。
- wtmp 兼容保留，但只覆盖系统实际写入的登录会话，不能保证非交互 SSH 都有记录；因此逐次 SSH 监控应使用 journal 或完整 authlog。

认证行没有终端时写 `N/A`，不虚构分配终端。已被操作系统清理的登录历史无法恢复。Linux 目标节点需要读取系统日志和 /proc 的权限。

## 通知接口

UDP 消息字段为 version、event_id、ip、host、time、type、data。每轮向每个配置地址发送 scan_summary（含 interval_seconds），以及逐条 alert 和 ssh_login。ip 默认使用本地出口地址，可由 agent_ip 固定；ssh_login 保留真实登录时间和稳定事件标识。通知发送结果写入本机报告。成功发送只表示本机网络栈接受，没有主控确认、重传或持久发送队列；本地日志/报告仍保存完整证据。

Agent 不接受远程指令、配置推送或远程控制。`server: []` 可独立运行全部本机检测。模板保留 `172.22.0.100:55555` 作为注释示例；主控接收存储和 Web 展示由各自服务负责。

## 部署与验证

`deploy/anqu.service` 是 -service 常驻服务；`deploy/anqu-oneshot.service` 与 `deploy/anqu.timer` 是可选外部调度方案，二者择一启用。从旧版本迁移时先停旧 timer，保留配置与状态备份后替换程序和单元。

自动验证覆盖文件生命周期、多对多允许值、递归搜索、缺失与读取错误、进程 OR 和白名单、实例数变化、每条登录和重启续读、日志跨北京时间午夜、UDP 本地数据报、历史指标系列唯一性、发布失败不推进状态，以及常驻调度出错后继续运行。旧版配置与内置加密构建测试继续执行。

Windows 上的模拟测试、加密 agent 冒烟运行以及 Linux amd64/arm64 交叉构建均已通过。此工作区没有可用的 Linux 运行环境，真实 /proc、journal、systemd、node_exporter 抓取和实际主控接收端仍需目标机验收。当前周期采样不能检测两轮之间发生又恢复的短暂文件或进程变化。
